# G plus G — контекст для Gemini

Этот файл — вводная карта для Gemini и других ИИ-разработчиков, работающих над
репозиторием вместе с Codex. Перед изменениями прочитай этот файл, `README.md`,
`CHANGELOG.md`, `docs/architecture.md`, `docs/implementation-status.md` и относящиеся
к задаче исходники. Не считай документацию доказательством работоспособности:
проверяй код, тесты и свежие логи.

## 1. Назначение продукта

G plus G — local-first desktop-приложение, которое без API управляет диалогом между
ChatGPT Web и Gemini Web через Playwright и видимые браузерные сессии пользователя.

Основной сценарий:

1. Пользователь создаёт локальный проект и задаёт вопрос.
2. Он выбирает режим и модель, отвечающую первой.
3. Приложение отправляет вопрос первой модели.
4. Вторая модель получает исходный вопрос, ответ первой и общий контекст проекта.
5. В режиме рассуждения модели ходят по очереди до независимого согласия или лимита.
6. История, решения, требования, метрики и ссылки на веб-чаты сохраняются локально.

Приложение не должно обходить CAPTCHA, проверки безопасности или ограничения
провайдеров. Авторизация выполняется пользователем вручную.

## 4. Локальные данные пользователя

На Windows основной каталог:

`%APPDATA%\multi-llm-orchestrator-feasibility`

В текущей пользовательской среде это:

`%APPDATA%\multi-llm-orchestrator-feasibility`

Ключевые данные:

- `orchestrator.sqlite` — проекты, разговоры, ходы, попытки, сообщения и события.
- `logs\application.jsonl` — журнал приложения.
- `logs\diagnostic-*.json` — отчёты об ошибках.
- `profiles\chatgpt` и `profiles\gemini` — изолированные браузерные профили.

Не печатай cookies, токены, содержимое Local Storage или другие секреты. Не удаляй
профили и базу без явного запроса пользователя и предварительной резервной копии.

## 5. Как устроен диалог моделей

Поддерживаются режимы:

- `MANUAL` / «Один ответ» — отвечает только выбранный первый провайдер.
- `SEQUENTIAL` / «Очередь» — каждый выбранный провайдер отвечает ровно один раз
  в заданном пользователем порядке.
- `PARALLEL` — независимые ответы на один вопрос.
- `DEBATE` / «Рассуждение» — модели ходят по очереди до согласия или лимита.

Для каждого проекта и провайдера есть одна запись `conversations` с `external_ref`.
После первой успешной отправки туда сохраняется фактический URL:

- ChatGPT: `https://chatgpt.com/c/...`
- Gemini: `https://gemini.google.com/app/...`

В следующем запуске `Orchestrator.prepareWebConversation()` обязан открыть этот URL,
а не корневую страницу. Не создавай новый веб-чат на каждый ход.

В `DEBATE` для каждого запуска формируется уникальный токен:

`[[G_PLUS_G_DONE:<runId>]]`

Модель добавляет его только если независимо считает решение согласованным.
Оркестратор прекращает дебаты, когда токен подтвердили оба провайдера. Токен
удаляется из пользовательского отображения и сохранённого ответа. Простое
копирование токена из ответа другой модели не должно считаться согласием.

## 6. Последние найденные ошибки и исправления

### Ложный logout ChatGPT

Раньше поиск слов `log in` по всему `body` мог принять текст разговора за экран
авторизации. Теперь приоритет имеют видимые login controls и доступный composer.

### Новый чат на каждый запрос

Раньше `external_ref` существовал в SQLite, но не использовался оркестратором.
Теперь URL сохраняется после успешного ответа и открывается в последующих запусках.

### Таймаут после нескольких успешных ходов

Лог `pre.7` показал `locator.fill: Timeout 30000ms exceeded`: React оставлял в DOM
старый `textarea`, который был видимым на момент выбора, затем становился disabled
или hidden. Дополнительно стабилизация текста могла завершить ход раньше полной
готовности UI.

В `pre.8`:

- composer считается пригодным только при `isVisible()` и `isEditable()`;
- ответ завершается только после исчезновения stop control, стабилизации текста и
  возвращения ровно одного доступного composer;
- правило действует для ChatGPT и Gemini.

На момент диагностики SQLite содержала постоянные ссылки обоих провайдеров; Gemini
не создавал новый чат, несмотря на визуальное ощущение перезагрузки страницы.

## 7. Команды разработки

Из корня проекта:

```powershell
npm install
npm run check
npm run desktop:start
npm run preflight
npm run release:info
npm run package
npm run smoke:packaged
```

`npm run check` обязан пройти перед коммитом: build, renderer/electron typecheck и
Vitest. Для изменений DOM-адаптеров статических тестов недостаточно: после сборки
нужен ручной live-прогон с несколькими последовательными ходами.

Установщики создаются в `release\`. Перед релизной сборкой сначала делай коммит,
потому что `scripts/write-build-info.mjs` встраивает текущий commit SHA.

## 8. Git и релизный процесс

1. Перед работой проверить `git status` и не затирать чужие незакоммиченные изменения.
2. Изменять только относящиеся к задаче файлы.
3. Обновить тесты и `CHANGELOG.md`.
4. Для релиза синхронно поднять версию в `package.json` и `package-lock.json`.
5. Запустить `npm run check`.
6. Создать содержательный локальный commit.
7. Запустить `npm run package`.
8. Запустить `npm run smoke:packaged`.
9. Поставить аннотированный тег версии.
10. Посчитать SHA-256 установщика и сообщить пользователю commit, tag и hash.

Не выполнять `git reset --hard`, не удалять чужие изменения и не делать push без
явного запроса пользователя. Бэкапы пользовательских данных должны быть
проверяемыми; существующие release checkpoints не перезаписывать.

## 9. Правила совместной работы Gemini и Codex

- SQLite и код — источник фактов; предположения подтверждать логами и запросами.
- Перед правкой адаптера читать свежий `diagnostic-*.json` и соответствующий stack.
- Не маскировать ошибки бесконечными retry. Каждый wait должен иметь предел, а
  неоднозначный DOM должен приводить к диагностируемой остановке.
- Не считать ответ завершённым только по таймеру: связывать его с новым DOM-узлом,
  отсутствием генерации и готовностью composer.
- Не сохранять чувствительные данные в логах, тестовых fixtures, Git или промптах.
- Изменения схемы делать только миграциями и сохранять обратную совместимость данных.
- При смене UI провайдера предпочитать несколько точных селекторов с проверкой
  видимости/редактируемости, а не широкие селекторы по всему документу.
- Любое архитектурное решение кратко фиксировать в `docs/architecture.md` или
  `CHANGELOG.md`, чтобы следующий ИИ понимал причину, а не только итоговый код.
- Если Gemini и Codex предлагают разные решения, сравнить их по воспроизводимому
  тесту, риску потери данных, устойчивости к DOM-изменениям и простоте отката.
- После внесения изменений оставлять рабочее дерево понятным: либо чистый
  проверенный commit, либо чёткий список незавершённых файлов и причин.

## 10. Ближайшие приоритеты

1. Live acceptance: длинные многоходовые диалоги обоих провайдеров.
2. Безопасные anonymized DOM fixtures для disabled/hidden/stale composer,
   streaming, empty response, rate limit и challenge.
3. Улучшение live-диагностики: provider, URL без query, selector chosen, состояния
   composer/stop control и длительность каждой фазы без сохранения текста/секретов.
4. Явное отображение в UI закреплённых URL разговоров и кнопка «Открыть чат», чтобы
   пользователь видел, что диалог переиспользуется.
5. Discrepancy review для спецификаций и подтверждение решений пользователем.
6. Только отдельным спланированным этапом — оценка переноса SQLite → PostgreSQL,
   включая миграцию данных, offline-режим и установку/обслуживание сервера.

Если фактический код расходится с этим файлом, сначала установи причину по Git,
тестам и логам, затем обнови и код, и этот документ.
