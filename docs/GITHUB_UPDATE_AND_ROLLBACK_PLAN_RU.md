# План обновлений через GitHub и безопасного отката

Статус: архитектурный план. В текущей ветке updater не реализуется, installer не
пересобирается, GitHub Release не публикуется и содержимое `release/` не меняется.

## Цели и границы

- Источник обновления — только GitHub Release официального репозитория.
- Production-канал принимает только подписанные стабильные теги `vX.Y.Z` из
  неизменённого SHA ветки `main`.
- UAT-сборки и feature-ветки никогда не предлагаются обычному пользователю.
- Проверка обновления не должна передавать проекты, тексты, cookies, токены,
  пути локальных файлов или provider-сессии.
- Автоматическая установка без явного согласия пользователя запрещена.
- Ошибка сети, GitHub API, подписи или checksum сохраняет текущую рабочую версию.

## Предлагаемая схема публикации

1. PR `uat -> main` проходит CI и ручной UAT на замороженном SHA.
2. На том же SHA создаётся аннотированный tag `vX.Y.Z`.
3. Из чистого checkout CI собирает Windows installer и update metadata.
4. Артефакты подписываются code-signing сертификатом; CI вычисляет SHA-256.
5. GitHub Release сначала создаётся как draft. В него входят installer,
   metadata, checksums, release notes и SBOM.
6. Отдельный verify job скачивает draft-артефакты, проверяет подпись, SHA-256,
   версию и clean-install/upgrade smoke.
7. Только после ручного approval release переводится из draft в published.

GitHub token для публикации существует только в защищённом CI environment. Он
не входит в приложение, installer, логи или update metadata.

## Клиентский lifecycle обновления

1. Проверка выполняется при ручном действии пользователя и, опционально, один
   раз после запуска с большим интервалом и jitter.
2. Клиент читает только стабильный channel и сравнивает SemVer. Downgrade,
   prerelease и смена channel отклоняются по умолчанию.
3. До загрузки UI показывает версию, размер и release notes.
4. Загрузка идёт во временный файл с ограничением размера. Проверяются HTTPS,
   конечный allowlisted host после каждого redirect, SHA-256 из metadata и
   Authenticode-подпись/издатель.
5. Установка предлагается только после успешной проверки и явного подтверждения.
6. Перед установкой приложение завершает активные операции, делает crash-safe
   checkpoint SQLite и резервную копию пользовательской БД/настроек без browser
   profile secrets.
7. После перезапуска новая версия выполняет health check и миграции в транзакции.
   Успех фиксируется отдельным маркером запуска.

## Совместимость данных

- Каждая схема SQLite имеет монотонный `schema_version`.
- Миграции обязаны быть идемпотентными и транзакционными.
- До release-кандидата проверяются upgrade с предыдущей stable и открытие копии
  реальной БД.
- Если новая версия записывает необратимый формат, бинарный downgrade не должен
  молча открывать его. Откат выполняется вместе с предобновленческой копией БД.
- Provider browser profiles не удаляются и не мигрируют без отдельного плана.

## Откат

Автоматический rollback допустим только до подтверждённого успешного health
check и только к заранее сохранённому, подписанному installer предыдущей stable.
Процедура:

1. остановить новую версию;
2. сохранить диагностический bundle без секретов;
3. восстановить предыдущий бинарник штатным installer;
4. при несовместимой миграции восстановить точную предобновленческую копию БД;
5. запустить read-only integrity check, затем обычный smoke;
6. показать пользователю результат и путь к локальной диагностике.

После успешного запуска новой версии автоматический downgrade запрещён: он
выполняется вручную по runbook. Отзыв плохого release делается снятием его с
канала и публикацией исправляющего patch release; существующий tag не
перемещается и артефакты под тем же номером не заменяются.

## Безопасность и наблюдаемость

- TLS недостаточно: обязательны allowlist hosts, checksum и проверка подписи.
- Логи содержат version, release id, стадии и коды ошибок, но не URL query,
  cookies, Authorization headers или пользовательский контент.
- Update metadata и release notes считаются недоверенным вводом и не могут
  исполнять команды/HTML.
- Необходимы таймауты, bounded retry только до начала установки и защита от
  параллельных update jobs.

## Gate перед реализацией

- письменное подтверждение владельца на updater и новый installer;
- успешный live file UAT ChatGPT/Gemini и persistence/recovery текущей фазы;
- выбор code-signing сертификата и защищённого GitHub CI environment;
- threat-model review, unit/integration tests metadata parser и redirect policy;
- clean install, upgrade N-1, interrupted download/install, offline mode,
  corrupted metadata, wrong signer/checksum, rollback и SQLite integrity;
- проверка на чистой Windows VM и отдельное ручное разрешение публикации.

До выполнения gate этот документ не является разрешением менять packaging,
добавлять `electron-updater`, собирать installer или создавать GitHub Release.
