# G+G: единый регламент и карта проекта

Этот файл — каноническая точка входа для сопровождения G+G. Он объединяет
уникальные правила и назначение документации, найденной во всех локальных
копиях проекта 2026-08-09. Одинаковые тексты из разных копий повторно не
переносились.

## Неприкосновенные правила работы

1. Если функция работает и это подтверждено проверкой, её не изменяют без
   воспроизводимой ошибки, требования владельца или доказанной необходимости.
2. Авторизацию ChatGPT и Gemini не изменять, не рефакторить и не «улучшать» в
   рамках общей разработки. Работа с ней разрешена только по отдельной прямой
   команде владельца и после фиксации рабочего контрольного состояния.
3. Единственный рабочий репозиторий на этом ПК:
   `C:\Users\onadl\OneDrive\Рабочий стол\G-plus-G`.
4. Одновременно переносится один логический блок. До следующего блока должны
   быть записаны точный commit/checkpoint, затронутые файлы и результаты
   проверок.
5. Нельзя писать «работает» только потому, что код выглядит правильным или
   собирается. Для каждого изменения используется один из статусов ниже.
6. Подтверждённый рабочий блок считается замороженным. Несвязанные изменения
   не должны затрагивать его файлы, публичные контракты и поведение.
7. Пользовательские данные, профили браузеров, cookie, токены, пароли и логи с
   секретами не удаляют, не копируют в Git и не выводят в отчёты.
8. Нельзя автоматически повторять вход, запускать частые проверки провайдеров
   или обходить CAPTCHA/защиту Google. Такие состояния требуют ручного действия
   владельца.
9. Откат должен быть точечным и обратимым. Запрещены широкие destructive-команды
   над рабочим столом, домашней папкой или всем репозиторием.
10. Изменения вносятся маленькими независимыми шагами: одна конкретная проблема —
    один узкий набор правок.
11. Для маленького шага выполняется только минимальная проверка затронутого места.
    Полный `npm run check`, упаковка и smoke-тесты запускаются только перед релизом
    либо по отдельной команде владельца.
12. Автоматический тест подтверждает только проверенный им контракт и не считается
    доказательством реальной работы функции. Статус `VERIFIED_USER` даётся только
    после ручной проверки владельцем.
13. Новый установщик не собирается после каждой правки: сначала ручная проверка в
    dev-режиме, затем отдельное решение о сборке.

## Статусы доказательства

- `VERIFIED_USER` — владелец вручную подтвердил требуемое поведение.
- `VERIFIED_AUTOMATED` — пройдены указанные сборки/тесты; ручной сценарий этим
  статусом не подтверждается.
- `UNVERIFIED_MANUAL` — автоматические проверки пройдены, но нужен ручной UAT.
- `UNVERIFIED` — доказательств работоспособности пока нет.
- `BLOCKED` — проверке мешает явно записанная внешняя причина.
- `FROZEN` — подтверждённая функция, которую нельзя менять без отдельного
  основания. Этот статус всегда сопровождается одним из `VERIFIED_*`.

## Архитектура и данные

G+G — Electron/React-приложение с общим orchestration core, адаптерами
провайдеров, локальным хранилищем проектов/ходов и управляемыми CLI-задачами.
Renderer обращается к main process только через preload/IPC. Провайдерские
адаптеры отвечают за сессию, отправку запроса, извлечение ответа и вложения;
оркестратор отвечает за раунды, контекст, финализацию и публичный transcript.

Исходный код и пользовательские данные — разные сущности. Репозиторий находится
на рабочем столе. Runtime-данные Electron находятся в
`%APPDATA%\g-plus-g` и не считаются лишней копией исходников. Их сохранность
обязательна при очистке и обновлении.

## Сохранённые продуктовые решения из исторических планов

- Текущая реализация Electron + React + TypeScript + Playwright + SQLite
  сохраняется. Ранний утверждённый план Chrome Extension + Native Host является
  историческим и не является командой на переписывание работающего приложения.
- Приоритет продукта — надёжный цикл ChatGPT Web + Gemini Web + Codex CLI +
  Gemini CLI. Расширение списка нестабильных провайдеров отложено.
- Базовые режимы: ручная передача, последовательный обмен, параллельный анализ,
  debate и отдельная финализация. Режим «Передать дальше» вызывает ровно одного
  следующего участника, а не перезапускает весь совет.
- В синтезированном режиме пользователь получает финальный ответ и понятный
  прогресс без внутреннего служебного transcript. В live-режиме Send меняется
  на Stop и возвращается после завершения/отмены.
- Визуальное направление: деловой интерфейс в чёрно-бело-оранжевой палитре,
  dark/light темы, SVG-иконки вместо emoji, человекочитаемые названия моделей,
  технические details под раскрытием и независимая прокрутка настроек.
- Длинная память разделяется на append-only Raw Journal, Decision Ledger со
  ссылками на источники и короткий Rolling Brief. Решение не перезаписывается
  молча: новая запись supersedes старую.
- Rollover выполняется до переполнения контекста через проверенный checkpoint и
  Continuation Pack. Новый чат обязан подтвердить цель, состояние и следующее
  действие; старый чат остаётся доступным.
- Активный production prompt не изменяется моделью автоматически. Допустим
  только PromptChangeProposal, затем пользовательское approval, eval и rollback.
- Secure Code Runtime с `G_PLUS_G_EXECUTION_V1` остаётся отдельным proposal. До
  выбора VM/container-grade изоляции разрешены схема/распознавание/UI, но нельзя
  выдавать обычный host process за sandbox или автоматически исполнять code fence.
- Текущий CLI-контур и будущий Secure Code Runtime — разные системы. CLI
  использует строгий `G_PLUS_G_CLI_TASK_V1`, approval, ограниченный workspace,
  структурированный argv и фактическую verification; он не даёт модели прямой
  shell и не обещает VM-изоляцию.

## Рабочий процесс изменения

1. Зафиксировать исходный commit и чистоту/известные локальные изменения.
2. Назвать один переносимый блок и перечислить ожидаемые файлы.
3. Проверить diff на случайное затрагивание авторизации и уже замороженных зон.
4. Выполнить одну минимальную проверку затронутого контракта. Общий gate
   запускать только на согласованном checkpoint, в CI, перед release либо по
   отдельной команде владельца.
5. Записать фактический результат в журнал ниже. Падение теста нельзя скрывать
   общим словом «готово».
6. Ручные функции оставить `UNVERIFIED_MANUAL`, пока владелец их не проверит.
7. Только после этого переходить к следующему checkpoint.

Git-история должна оставаться линейной и понятной: одна причина — один commit;
никаких force-push и смешивания несвязанных исправлений. Перед релизом нужны
build, test, typecheck, проверка установщика/обновления/rollback и UAT evidence.

## Безопасность

- CLI-команды требуют явного scope, approval и проверки пути; запрещены
  shell-инъекции, выход через symlink и запись в защищённые области.
- Вывод задач ограничивается по размеру и очищается от секретов.
- Вложения валидируются по существованию, типу, размеру и принадлежности
  проекту; временные копии удаляются после использования.
- Transcript хранит публичный ответ и идентификатор фактического провайдера;
  внутренние reasoning/секреты в него не попадают.
- Повреждённое локальное состояние не должно приводить к тихой потере данных:
  нужны диагностика, резервная копия и явная ошибка.

## Приёмка

Минимальный gate микрошагa: одна связанная проверка затронутого контракта и
просмотр diff. Для согласованного checkpoint дополнительно выбирается только
необходимая сборка/typecheck. Полный релизный gate включает desktop build,
пакетирование, чистую установку,
upgrade/rollback, перезапуск, сохранение проектов, ручные сценарии провайдеров,
вложения, длинный диалог, cancel/retry CLI-задач и проверку журналов на секреты.

Проверка авторизации не входит в текущую миграцию. Если владелец позднее даст
отдельную команду, она проводится вручную с низкой частотой и без автоматических
повторов.

## Известные ограничения

- Успешная сборка не доказывает работоспособность внешнего провайдера.
- CAPTCHA, anti-bot, изменение DOM и внешняя сеть не контролируются приложением.
- Одновременное использование одного persistent browser profile несколькими
  процессами может вызвать блокировку профиля.
- Некоторые UAT-сценарии требуют реальных аккаунтов и потому остаются ручными.
- Исторические repair-пакеты и отчёты могут описывать уже устранённые дефекты;
  они не имеют приоритета над текущим кодом и журналом доказательств.
