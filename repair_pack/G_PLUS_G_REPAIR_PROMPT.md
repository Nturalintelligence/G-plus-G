# G+G — план восстановления интерфейса и логики

## Роль и режим работы

Ты работаешь внутри существующего проекта G+G. Твоя задача — восстановить продукт после неудачной переработки, не переписывая приложение с нуля и не меняя подтверждённую архитектуру без доказанной необходимости.

Работай последовательно. После каждого этапа запускай проверки и показывай пользователю: изменённые файлы, выполненные команды, результат тестов и 1–3 скриншота. Не переходи к следующему этапу при красных тестах. Не заменяй реальные функции статическими макетами.

## 0. Обязательная разведка до правок

1. Найди фактический корень репозитория и прочитай `package.json`, `GEMINI.md`, `CHANGELOG.md`, Electron main/preload, React renderer, CSS, оркестратор, browser runtime, adapters, storage и observability.
2. Проверь `git status` и сохрани список уже изменённых файлов. Не откатывай пользовательские изменения и не используй destructive-команды.
3. Найди последний проект «тест салон». Проверь его проекты, turns, messages, events и `logs/application.jsonl`.
4. Установи точную причину состояния «прогресс виден, приложение/ответ не виден»: зависший FSM, ошибочная фильтрация SYNTHESIZED, потерянный IPC-event, render exception, неверный active project, незавершённый finalizer или иной подтверждённый источник.
5. Сопоставь описание проекта с реальным кодом. Не считай существующими `TwoTierOrchestrator`, `CliExecutorBridge`, headless-режим или IPC handlers только потому, что они перечислены в документации.
6. До реализации выдай короткий audit report: подтверждено / отсутствует / сломано / причина сбоя / минимальный набор исправлений.

## 1. Зафиксированные продуктовые правила

- Приложение: local-first Electron + React + TypeScript + SQLite + Playwright.
- Обычные сессии ChatGPT/Gemini/DeepSeek работают в фоне и не создают всплывающих окон.
- Видимый браузер разрешён только для входа, CAPTCHA, повторной авторизации и явного ручного восстановления. После успеха окно закрывается, профиль продолжает работу в фоне.
- Никакого обхода CAPTCHA, антибот-защиты или ограничений сервиса.
- Существующие профили, URL закреплённых чатов, проекты, история, события и настройки должны сохраниться.
- Запрещено переписывать приложение целиком, подменять функциональность моками и удалять рабочие функции ради дизайна.

## 2. Визуальное направление

Сделай спокойный big-tech UI: смесь ясности Apple, композиции ChatGPT, тёплого акцента Claude и компактных действий Telegram. Не копируй компоненты брендов буквально.

Палитра:

- dark background `#0B0B0C`, elevated `#151516`, text `#F7F6F2`;
- light background `#F7F6F2`, elevated `#FFFFFF`, text `#121212`;
- accent `#D8653B`; accent-hover `#BC4F2B`;
- нейтральные границы с низким контрастом, без оранжевых рамок вокруг каждого блока.

Требования:

- единая система spacing 4/8/12/16/24/32;
- радиусы 8–14 px, без бесконечных pill-контролов;
- нормальные SVG-иконки из одного набора; эмодзи в интерфейсе запрещены;
- состояния hover, active, focus-visible, disabled, loading;
- WCAG AA для основного текста и клавиатурная навигация;
- интерфейс не должен ломаться при 1024×700, 1280×720, 1440×900, 1920×1080 и при масштабировании 125–150%;
- не делать glow, градиентные рамки, glassmorphism, псевдо-3D и «геймерский» интерфейс.

## 3. Каркас приложения

### Верхняя панель

- Удали маленький логотип рядом с названием.
- Замени `G+G — Autonomous AI Engine` / `Multi-Model Workspace` на деловое `G+G Workspace`.
- Кнопка сайдбара — настоящий hamburger из трёх горизонтальных линий, без символа `≡` и без эмодзи.
- Сохрани системный title bar Electron; не дублируй навигацию.

### Сайдбар

- Ширина 272 px в раскрытом состоянии, плавное схлопывание; основной контент всегда перерасчитывает ширину.
- Проекты оформить компактным списком чатов как в ChatGPT: название, активное состояние, контекстное меню по `…`; не показывать отдельную корзину в каждой строке.
- Удаление — через меню и подтверждение.
- `Новый проект` открывает modal с обязательным названием и необязательным описанием. Удали старое постоянно видимое поле/панель создания.
- Ниже проектов — раздел `Модели`: официальный/предоставленный логотип, имя, состояние `Готова / Требуется вход / Занята / Ошибка` и ненавязчивый status-dot.
- Нижняя плашка пользователя открывает настройки. Отдельную кнопку настроек удалить.

## 4. Настройки

- Сделай адаптивное окно или отдельный экран минимум 900×620.
- Слева фиксированное оглавление, справа только выбранный раздел.
- Скроллится правая область, заголовок и навигация остаются на месте.
- Разделы: `Профиль`, `Модели и авторизация`, `Обсуждение`, `Итоговый ответ`, `Интерфейс`, `Данные`, `Диагностика`.
- Список моделей не должен обрезаться на небольшой высоте.
- Кнопки `Сохранить` и `Отмена` закрепить в footer. `Сбросить` сделать вторичным опасным действием с подтверждением.
- Убрать эмодзи, fieldset-легенды и оранжевые рамки выбранного раздела.

## 5. Закреплённые веб-чаты

- Плашка кликабельна целиком.
- По клику справа выезжает drawer со списком моделей, URL чата, статусом и действиями `Открыть`, `Перепривязать`, `Скопировать ссылку`.
- Не открывать браузер автоматически при раскрытии drawer.
- Открытие веб-чата происходит только по отдельному действию пользователя.

## 6. Композер

- Расположи панель режимов непосредственно над полем ввода внутри единого composer-shell.
- В свернутом виде показывай краткое резюме: режим, участники, финализатор. По клику панель раскрывается вверх и не перекрывает текст.
- Поле растёт по содержимому до заданного максимума, затем получает внутренний скролл.
- Поддержи paste/drag-and-drop/file picker для изображений и файлов.
- Вложение показывай миниатюрой 48–64 px с именем и кнопкой удаления. По клику изображение открывается в полноэкранном preview modal с закрытием по Escape и клику на фон.
- Справа одна action-кнопка с SVG-иконкой бумажного самолётика. После запуска она атомарно превращается в Stop; Stop вызывает AbortController/IPC cancel, останавливает текущий run, сохраняет согласованное состояние и возвращает кнопку Send.
- Не использовать emoji `📤` и `⏹️`, текст внутри круглой кнопки и коричневый фон.

## 7. Режимы отображения

### Готовый ответ / SYNTHESIZED

- Не показывай промежуточные сообщения моделей и скрытые peer-prompts.
- Показывай компактную анимацию этапов: `Анализ задачи → Обсуждение → Проверка → Подготовка ответа` с именем активной модели, длительностью и возможностью Stop.
- После согласования запусти ровно один finalization-turn и покажи только его структурированный результат.
- Ошибка одной модели не должна оставлять вечную анимацию: показывай recoverable error и действия Retry/Continue without model/Stop.

### Обсуждение / LIVE

- Название LIVE не означает DOM-token streaming. Сначала дождись полного стабильного ответа адаптера и запиши его в SQLite.
- Затем плавно раскрой сохранённый текст в UI контролируемой анимацией. Остановка визуальной анимации не должна повредить сохранённое сообщение.
- Показывай модель, роль, номер хода, время и состояние. Служебные prompts пользователю не показывать.

## 8. Выбор финализатора

Добавь `finalizerMode`:

- `MANUAL`: пользователь выбирает конкретного провайдера. Этот выбор абсолютен: модель формирует итог независимо от её позиции в цепочке.
- `LEAD_SELECTS`: главный ИИ выбирает финализатора один раз и возвращает машинно-читаемое решение, которое валидируется по списку активных моделей.
- `PEER_AGREEMENT`: если участников ровно двое, первый короткий служебный раунд выбирает одного финализатора; при конфликте используется стабильный fallback, заданный настройками проекта.

Выбор фиксируется в run до первого содержательного хода и не меняется молча. Если выбранная модель недоступна, запроси решение пользователя или используй заранее выбранный fallback — не подменяй её автоматически.

Finalization prompt обязан содержать: исходную задачу, каноническое резюме согласованных решений, открытые риски, требования к формату и запрет продолжать дебаты. Не пересылай бесконечно всю DOM-историю.

## 9. `Передать дальше`

- Это одноразовый handoff следующему выбранному участнику, а не новый полный run.
- Сформируй компактный payload: исходная задача, последний принятый ответ, релевантные решения и конкретная инструкция следующему ИИ.
- Никогда не показывай и не добавляй в пользовательский чат фразу `Проверь и развей следующий ответ другой модели.`
- Не пересылай всю историю повторно и не прогоняй всех участников.
- Получи один ответ, сохрани его как следующий turn текущего run и остановись.
- Защити действие `handoff_id`/idempotency key от двойного клика и повторной отправки.

## 10. Логотип и splash screen

В пакете даны:

- `gg-logo-dark.svg` — для тёмного фона;
- `gg-logo-light.svg` — для светлого фона.

Подключение:

1. Положи их в `apps/desktop/renderer/assets/brand/`, сохранив имена.
2. Импортируй как URL через сборщик или используй `<picture>`/theme selector. Не вставляй base64 и не копируй SVG-разметку в React-компонент.
3. Splash: знак 96–120 px, `object-fit: contain`, без растяжения, свечения и дополнительного круга. Под ним только `G+G Workspace` и короткое `Подготовка рабочего пространства…`.
4. Dark theme использует `gg-logo-dark.svg`, light theme — `gg-logo-light.svg`. Переключение должно реагировать на сохранённую тему до первого paint, чтобы не было белой вспышки.
5. Для sidebar/header используй только текст `G+G Workspace`; знак там не дублировать.
6. Для Electron icon создай отдельные `.ico`/`.png` из геометрии знака штатным build script, с безопасным padding 12–16%. Не используй широкую концептуальную картинку как app icon.
7. Не изменяй пропорции SVG и не накладывай свои градиенты/тени.

## 11. Надёжность и данные

- UI подписывается на состояние run из единого store; прогресс и итог не должны жить в несвязанных локальных `useState`.
- Все переходы `RUNNING → FINALIZING → COMPLETED|FAILED|CANCELLED` сохраняются до UI-event.
- При перезапуске незавершённый run восстанавливается из SQLite/event journal.
- IPC события имеют `runId`, `projectId`, `turnId`, sequence и typed payload; renderer игнорирует события чужого проекта, но не теряет их в repository.
- Скрытие промежуточных сообщений в SYNTHESIZED — только presentation filter, а не удаление из БД.
- Логи не содержат пароли, cookies, токены и полный текст пользовательских запросов.

## 13. Проверка и критерии приёмки

Запусти существующие `lint`, typecheck, unit/integration tests и package/smoke команды из реального `package.json`. Не выдумывай названия скриптов.

Обязательные сценарии:

1. «тест салон» открывается, история и итог видны; нет вечного progress.
2. Обычный run не показывает браузер; login показывает; после login окно закрывается.
3. SYNTHESIZED скрывает обсуждение и показывает один ответ выбранного финализатора.
4. MANUAL Gemini возвращает итог при любой позиции Gemini в очереди.
5. Две модели выбирают финализатора один раз; конфликт обрабатывается детерминированно.
6. LIVE получает полный ответ, сохраняет его и только затем анимирует отображение.
7. Stop прекращает run и после завершения отмены снова становится Send.
8. `Передать дальше` вызывает только одного следующего участника один раз.
9. Paste screenshot показывает миниатюру; клик открывает preview; Escape закрывает.
10. Settings прокручиваются и доступны при высоте 700 px.
11. Sidebar и composer не исчезают и не перекрываются на всех контрольных разрешениях.
12. Тёмная/светлая темы выбирают правильный SVG без layout shift и white flash.

Финальный отчёт должен содержать: первопричину исходного сбоя, список изменённых файлов, миграции данных, результаты тестов, оставшиеся ограничения и скриншоты контрольных состояний. Не объявляй работу завершённой при сломанной сборке, красных тестах или непроверенном packaged-приложении.
